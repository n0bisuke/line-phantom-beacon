# 「動いたら LINE が鳴る疑似ビーコン」を Wi-Fi 電波だけで作った(M5Stack AtomS3 × ESPectre × LINE Messaging API)

*2026-11 / M5Stack AtomS3 / ESP32-S3 / PlatformIO / ESPectre v3.2.0*

## はじめに

つくったのは、**Wi-Fi の電波(CSI)の乱れだけで「人やモノの動き」を検知して、LINE に push する疑似ビーコン**です。

- センサー専用のデバイスを追加せず、AtomS3 1台
- サーバー不要。ESP32 から LINE Messaging API へ**直接 HTTPS push**(サーバーレス)
- 通知は3段階に設計: 動き検知 → 10秒無動作 → 20秒無動作 → 30秒で「寝落ち」疑い。以降は黙る
- LCD にも状態が出る(緑 = MOVE、暗青 = LEAVE、紫 = SLEEP、暗赤 = NO-WIFI)

「動きがない = 退室」や「動きがない = 就寝」を断定するものではなく、擬似イベントであることを通知文言でも明示しています(本記事も同様)。

```
[M5Stack AtomS3] -- Wi-Fi CSI で動き検知(ESPectre)
                -- HTTPS push ---> LINE Messaging API ---> スマホ
```

## なぜ Wi-Fi だけで動きがわかるのか

Wi-Fi Chip は受信した 802.11n パケットの中で、OFDM の各サブキャリアごとの振幅・位相を **CSI(Channel State Information)** として出力します。空間の人や物はこの伝送経路を乱すため、CSI の推移に「動き」が現れます。

ESP32-S3 では [ESPectre](https://github.com/francescopace/ESPectre) が CSI 抽出 → 移動エネルギー算出 → 閾値判定 → デバウンス済みの `motion` イベントまでを自動でやってくれます。キャリブレーション(約30秒、部屋を空けておく)が済むと `ready` になり、以後は `onMotion(bool)` コールバックだけで良い感覚です。

### ここで一番躓いた点: CSI が流れない

初日は「movement が 0 のまま進まない」。原因は ESPectre の既定のトラフィック生成が **PING(ICMP)** だったこと。CSI は「受信パケット」から取る必要があり、誰もパケットを送らないと電波が流れない。そこでライブラリは ICMP ping を Gateway に打ってCSI を供給するのですが、**iPhone のテザリングは ICMP を弾く**ので CSI が完全に枯れました。

→ 設定を `TrafficGeneratorMode::WIFI_RAW`(Null Data フレーム + ACK で自前トラフィック)に切り替えたら、テザリング環境でも `occ=1.00 / admitted=100pps` で安定。

```
[csi] gen_pps=100 rx_pps=0 accepted_pps=100 admitted_pps=100 occ=1.00
```

教訓: **CSI を使うプロダクトは「トラフィックの供給方法」を必ずプロトコル面で確認する**。ICMP 通すか / 802.11n 2.4GHz を許すか、は Wi-Fi AP の仕様次第です。

## 疑似イベントの設計: 3段階 + 「黙る」

最初は「10秒静かになったら push」だけでした。しかしこれだと「10秒たった」と一言しか伝わらず、延々 push が続くか、何も起きないかのいずれかになる。最終形は、仕様も含めてこう:

| タイミング | push | LCD |
|---|---|---|
| 動き検知 | 🏃 動きを検知しました(擬似) | 緑 `MOVE` |
| 10秒無動作 | 🚪 動きがなくなりました(○秒...) | 暗青 `LEAVE` |
| 20秒無動作 | 🚪 継続して動きがありません(○秒...) | 暗青 + カウント継続 |
| 30秒無動作 | 😴 寝落ちの可能性(○秒...) | **紫 `SLEEP` + カウント延長戦** |
| 以降 | **push しない** | 紫のままカウントは続く |

ポイントは「**静観期間中、同じ段階を 1 回しか通知しない**」+「**最終段階(寝落ち)より下位の通知を遅延発火させない**」+「**寝落ち以降は黙る**」。3点とも `lib/phantom_events/` に純 C++ で切り出してあるので、ネイティブテストで遷移を全部保証しています(17テスト)。

- `motion==true` が続く限り keep-alive して、動き続けても pseudo leave を発火させない
- 起動直後に検知実績ゼロの静止では「空室通知」をしない
- 文言の秒数は `PSEUDO_LEAVE_MS` 等の定数から自動生成(しきい値を変えれば文言も追従)

### ノイズで push が連発した問題と ready gating

ある日、静止しているのに 🏃→🚪→👋 が順番に通知されました。原因は**センサーが ready(信頼状態)と waiting を往復**していたこと。CSI 品質は日当・人数・AP の位置で数時間ごとに変わります。

→ 「ready の間だけ疑似イベントを評価し、ready が落ちた期間の motion/静止は無視、復帰時に `reset(now)` で状態機を初期化」としました。これにより ready 往復しても push が回転しないようになっています。

### 計測のズレ問題: 「画面は 16s で push が出る」

「10秒固定のはずが 16 秒くらいで push される」という指摘が実機検証で出ました。原因は、LCD のカウントが「**motion の立ち上がりエッジ**」から再計算していたのに対し、push の10秒計測は「**motion 状態が解除されてから**」走っていたこと。ESPectre の motion は物理的に手を止めてから**数秒間ホールド**するので、時計の起点が6秒程度ズレていました。

→ motion 状態が true の間は同じ時計を更新し続け、両方を「motion 解除後10秒」に統一しました。LCD と push が完全に同調します。逆に言うと「手を止めてから push まで」は 10秒 + 数秒(デバウンス分)です。誤検知を抑える正しいトレードオフです。

## 通知の実装: サーバーレスで LINE へ直push

中継サーバー(Node.js)案もいったん作りましたが、「pushだけだからサーバーいらないよね」という判断で構成を**ESP32 直push のみ**に簡素化しました。

- `POST https://api.line.me/v2/bot/message/push` (Bearer トークン認証)
- ESP32 側で TLS 接続が正当な CA によるものか検証(`setInsecure()` は使わない)
- LINE サイトの認証が GlobalSign 発行だったので、中間証明書 + ルート証明書を公開情報としてヘッダーに同梱(`src/line_root_ca.h`。2029年まで有効)
- 無料プランの push 上限(月200通)を保護するため、type ごとに最小間隔で抑止(動き系10秒/静止系30秒)
- LINE チャネルトークン・Wi-Fi パスワードは `include/secrets.h`(gitignore済み)にのみ存在

```
[line] pushed pseudo_leave
[line] push sleep_suspected failed: 401 (トークン失効?)
```

## LCD での UX 設計

AtomS3 は 128x64 の小さな LCD。Font0 の8px では小さすぎるので:

- 上段は Font2(16px)で `W:on R1 mv:0` の補助情報(状態が LEAVE / SLEEP のときはその文字に差し替え)
- 下段はサイズ3の**大きい秒数カウント**。状態は背景色で示す(通常黒 / MOVE 緑 / LEAVE 暗青 / SLEEP 紫)
- Wi-Fi が切れたら `NO-WIFI`、キャリブレーション中は `CALIB`(動かさず待ってと言う意味)

「正常系がわからない」というフィードバックが実装初日にあり、表示仕様を README に明文化したのは大きな改善でした。小さい組み込み系では、**何が正常で何が異常かを画面で語る**だけで操作性とデバッグ速度が大幅に上がります。

## 落ち穂拾い集

- **`pio device monitor` を開くと AtomS3 がリセットされることがある**。ログ的には `rst:0x15 boot:0x20 DOWNLOAD(USB/UART0)`(USBダウンロードモード待ち)。`monitor_rts=0/monitor_dtr=0` を `platformio.ini` に設定しておくと防止効果あり。たまたま落ちたときは(USB が接続されている限り)再アップロードで復帰します
- `No serial data received` は USB の列挙が固まったパターン: ケーブル抜き差しでほぼ回復
- ESP32-S3 でシリアルログを出すボード定義(`m5stack-atoms3`)には `ARDUINO_USB_CDC_ON_BOOT` がないので、`build_flags = -DARDUINO_USB_CDC_ON_BOOT=1` は必須
- テストは `pio test -e native` でボード無しに回せるよう、状態機・BEACONフレーム生成は純C++に切り出し
- Wi-Fi は複数 AP 登録対応。切れたときだけスキャンしなおして最も RSSI の強い AP に切り替え、**繋がっている間は切り替えない**(CSI の再キャリブレーション防止)

## まとめ

1. **CSI ベースの動き検知は、センサー追加なしの部屋監視として実用レベルに届いた**。ただし Wi-Fi AP の仕様(ICMP / 2.4GHz / 802.11n)に依存する点は設計時に必ず押さえる
2. **「擬似イベントを何段階にするか」は通知の設計次第で使いやすさが全く変わる**。最も重要なのは「もう黙る」タイミングも設計すること
3. **実機検証のフィードバック(表示のズレ、通知の連発)が設計を良くした**。状態機は純C++に切り出してテストすることで、このループが早く回った

この一連の手順を GitHub Codespaces で試せるハンズオンとしてまとめたのが [docs/handson.md](handson.md) です。
